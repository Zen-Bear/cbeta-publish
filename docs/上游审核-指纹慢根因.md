以下"实测"均为 publish 仓只读脚本测得（真实用户配置，T0220 与《藏要》第一辑）；
"比对"指逐行 diff 上游版本。结论若与上游实现不符请指正，
尤其是第 4 节（publish 侧自查出的疑似协议误用）。

## 1. 现象

| 项目 | 数值 |
|---|---|
| 单次 `verify_fingerprint`（现） | 约 1.8–2.0 秒（冷缓存更高，曾测得单次 5.9 秒） |
| 同量级此前（基线根为空时） | 约 13–36 毫秒 |
| 《藏要》第一辑准备阶段（29 部 × 3 格式 = 87 次） | 约 177 秒 |
| 同内容直接列目录定位 | 约 2.6 毫秒 |

## 2. 根因

调用链（publish 按部 × 格式逐次调用，调用间无共享）：`cbeta_publish/gui/main_window.py:6017` → `cbeta_publish/books/xml2pdf_bridge.py:1546`（生效预设有快照复用，约 5 毫秒，可忽略）→ 上游 `pycbeta/verify.py:2689` → `pycbeta/verify.py:2766`（`_official_superset`）→ `pycbeta/verify.py:1652` → `pycbeta/verify.py:1677`（`_find_official_in`）递归通配符扫库。

耗时拆解（T0220/pdf，同一环境）：预设约 5 毫秒；`canonical_verify_config` 约 5 毫秒；`_impl_digest` 约 0.8 毫秒；基线发现约 1.76 秒（txt_notes 约 1.4 秒：5 组通配符 × 27,049 文件；docx 约 0.33 秒）；链内文件哈希可忽略（pdf 链只取 1 个 html）。

反直觉但已实测：卷限定到单卷（卷 479）仍约 1.77 秒——卷过滤发生在枚举之后，扫量不变。

触发条件：`E:\dev\cbeta\xml2pdf\presets\config.user.json` 的 `source.baselines` 从空串改为指向 `E:\CBETA\2026r2` 下三个库根（10-14 14:01 的工作区改动；v0.9.1 包已带入）。此前只扫工作目录。

放大系数：87 次调用；不新鲜项在上游导入判定（`cbeta_publish/gui/main_window.py:5997`）还可能重算一次。

## 3. 排除项（已逐行比对）

- 上游 v0.9→v0.91：`_verify_fingerprint_inner` 零差异；`_find_official_in` 只加 `strict_juan` 过滤；`_official_superset` 在 1113d97→88ba086 零差异（87acf77→88ba086 仅 epub/odt 纳入卷过滤与 strict 透传，不加扫描量）。
- report.json 的 v0.91 改动（`baseline_coverage`、差异段封顶）不在指纹链路上。
- 指纹版本 `verify-fp-1` 未变（单一历史提交引入），旧记录未因此批量失效。

## 4. publish 侧的指纹协议理解（请审核指正）

- 目的：廉价预检"上次 pass 结论是否仍然有效"，有效则跳过真校验。
- 载荷（`pycbeta/verify.py:2689`）：fp_version、work、requested、coverage、XML 文件身份列表（名/大小/mtime_ns/sha256）、config_digest、baselines（链解析后各文件身份）、thresholds、t2s/engine/vertical/baseline、impl、juan（子集才有；整本无该键以保旧记录有效）。
- 绑定逻辑：XML 源（输入）＋官方基线（比对基准）＋生效配置＋阈值＋实现＋卷范围；任一变则重验。基线缺席返回空（一律重验）。指纹与真校验共用 `_official_superset`（同卷过滤、同格式链），保证"证明的正是实际要比对的那批文件"。
- 复用通道：本机 `config/verify_records.json`（记指纹＋输入集＋卷＋接受档；`is_fresh`（`cbeta_publish/books/verify_cache.py:109`）全中且产物在库才跳过）；上游 `report.json`（真校验写入同一指纹；publish 跨边导入时重算比对）。
- publish 调用方式自查（疑似误用，请确认）：按部 × 格式逐次调用，未用 `_ctx` 共享同部书的发现结果（上游文档注明 `_ctx` 供"一次发现多格式复用，避免每格式重扫基线目录"）。若确认，publish 侧可改（约省 2/3 重复扫描），但单次 1.8 秒仍需上游修。
- 存疑点（实测与文档不符）：`pycbeta/verify.py:2485` 注释与 `docs/上游-P2校验结论跨边复用提案.md:23` 均称 mtime_ns 只记录不哈希；但实测同内容仅 mtime 加 1 指纹即变。请确认以何为准（若剔除，同字节重写不再误触发重验；但改 `verify.py` 会触发下节副作用）。

## 上游答复（xml2pdf 侧，2026-10-14）

**结论：第 2 节根因成立；问题定性为「发现实现（主因）＋ 调用方式（次因）＋ 一处协议语义（mtime）」，指纹协议整体设计不变。** 已按第 5 节方向修复并实测，逐条回应如下。

### 一、逐条核对

| 你们的主张 | 上游核对 |
|---|---|
| §2 递归通配符扫库是耗时大头（txt_notes 5 组 × 27,049 文件 ≈ 1.4 s；docx ≈ 0.33 s） | **成立**，实测同量级；"卷限定到单卷仍 1.77 s"也对——卷过滤发生在枚举之后 |
| §2 触发条件是 `source.baselines` 指向大库根 | **成立**；未配置时只扫工作目录（13–36 ms） |
| §3 v0.9→v0.91 指纹链零差异（仅 `strict_juan` 与卷过滤透传） | **核对一致** |
| §4 按「部 × 格式」逐次调用、未复用 `_ctx` 属误用 | **成立**；`_ctx` 可传 `{presets, canon, official, impl}` 跳过重复解算与发现 |
| §4 mtime 存疑（文档称不哈希、实测会变） | **你们对**：载荷直接内嵌 `_file_identity` 四元组，`mtime_ns` 实际参与了哈希；那句注释与 `上游-P2校验结论跨边复用提案.md` 的措辞都不准确 |

### 二、已落地的修法（对应 §5）

1. **发现提速**：`_find_official_in` 先按集中库布局直接定位——`{根}/{canon}/{work_id}/{work_id}_{NNN}.{ext}`（html / txt_notes / docx）与 `{根}/{canon}/{work_id}.{ext}`（epub / odt）；未命中才回退原有通配符。采纳你们的规则，但**复用 fetch 侧已有的布局与命名知识**（避免两处布局知识漂移），回退粒度定为「（根，格式）为空才回退」。
2. **协议语义**：指纹载荷的文件身份改为 `{name, size, sha256}`（**不含 `mtime_ns`**）⇒ 同字节重写、基线重下都不再误触发重验。`report.json` 的公开 `inputs` / `baselines` 仍按提案 §4.2 记 `name/size/mtime_ns`（不含 sha），两者口径互补。
3. **指纹版本**：`verify-fp-1` → **`verify-fp-2`**；同时修掉一处硬编码——返回串此前写死 `verify-fp-1`，所以"升版本号不会体现在串上"（这也是你们观察到"版本未变"的原因）。
4. **文档**：`docs/校验report.json说明.md` §4 增补 `_ctx` 用法与上述语义；`docs/上游-P2校验结论跨边复用提案.md` 修订 mtime 措辞。

### 三、实测（上游，T1579 + 三个库根）

| 场景 | 修前 | 修后 |
|---|---|---|
| 单次基线发现（txt_notes 100 卷 + docx 100 + epub 1） | **1738 ms** | **45.9 ms**（发现本身约 10 ms，其余为基线哈希） |
| 结果集合与顺序 | — | **完全一致，指纹逐字相同** |
| 工作目录型根（T1579 自带基线） | 4.9 ms | 5.3 ms（结果一致） |

单测锁死：库布局与通配符同集合/同顺序、卷过滤一致、非库布局回退；另有"仅 mtime 变不改指纹"的回归用例。

### 四、给下游的两点

1. **`_ctx` 复用**：按「部」算一次 `{presets, canon, official, impl}`，传给该部各格式的 `verify_fingerprint(..., _ctx=…)`，可再省约 2/3 重复扫描（`presets=` 与 `_ctx=` 两种传法结果逐字一致）。
2. **一次性失效**：改 `verify.py` 会让已存指纹记录失效一轮（`_impl_digest` 含 verify 自身，且载荷已升 `verify-fp-2`）——修后首次整体重验，之后恢复正常。
